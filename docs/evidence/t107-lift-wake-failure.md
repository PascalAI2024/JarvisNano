## Diagnosis

`imu_ctrl9()` used fifty iterations of `pdMS_TO_TICKS(2)` per handshake phase.
This build has `CONFIG_FREERTOS_HZ=100`, so the requested delay was zero ticks.
The purported 100 ms polling interval was only bus transaction time and
scheduler yields. The function acknowledged even without observed completion,
ignored read and ACK errors and clear timeout, and returned `ESP_OK`.
Consequently `armed.lift=true` proved software admission, not successful
hardware command completion or an interrupt generated by the lift.

The A datasheet physical page 44 / printed page 43 requires completion at
STATUSINT bit 7, then CTRL9 `0x00` ACK and completion clear. The repair uses
a real 100 ms elapsed deadline for each phase with a minimum one-tick delay,
ACK only after observed completion, and propagated errors/timeouts.
Unconfirmed WoM configuration is now reported as `lift_fail=arm_failed`
and lift is not advertised as armed; touch/timer fallback remains available.

The threshold remains 100 mg at about 21 Hz. CAL1_H `0x20` correctly selects
INT1 initially low plus 32 startup blanking samples (about 1.52 s), consistent
with GPIO21 EXT0 high. The wake coordinator keeps RTC peripheral power on and
uses actual deep sleep; the touch reset and retained count corroborate sleep.
At the initial failure checkpoint, gentle-lift sensitivity, actual interrupt
delivery and board routing remained unproven alternatives. The repaired lift
retest below supports the arming defect as the cause, without an electrical
interrupt measurement. No threshold or GPIO guess is included.

N10.4 records an earlier board observation that CmdDone did not appear,
with either handshake type. This makes a post-OTA arming gate necessary:
strict completion may report `arm_failed` rather than restore lift. That
result would keep acceptance failed and require measured protocol/interrupt
diagnosis; a host fake is not hardware proof.
